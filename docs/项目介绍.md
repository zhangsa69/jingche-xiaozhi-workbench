## 一、一页速览

| 项目 | 内容 |
|---|---|
| 产品名称 | 京车小智工作台（英文代号 PI-Desktop） |
| 产品形态 | 跨平台桌面应用（Windows / macOS / Linux） |
| 一句话定位 | 让 AI 智能体在一个独立、可控、数据留在本机的桌面环境里，真正把活干完 |
| 解决的核心问题 | 现有 AI 编程工具要么被终端束缚、要么被编辑器绑定、要么把数据与模型锁在云端 |
| 关键差异 | 不绑账号、不走强制中转、不锁定模型、不绑定编辑器 |
| 目标用户 | 开发者、技术团队、技术管理者、需要快速形成会议纪要的业务团队 |
| 技术底座 | Electron 桌面外壳 + React 界面 + Rust 特权内核 + 独立 Agent 运行时 |
| 能力范围 | 项目与会话管理、三种工作模式、多模型接入、权限管控、变更审阅、任务委派、插件生态、会议纪要生成 |
| 当前阶段 | 早期预览（Early Preview），核心链路可用，接口与部分行为仍在演进 |
| 规划中的新能力 | 会议纪要生成模块（录音 → 转写 → 分人 → 总结 → Word 导出），全链路本地完成 |

**给决策者的三句话：**

1. **它不是一个聊天窗口，而是一间给 AI 用的办公室**——项目、文件、改动、权限、审批、长期任务都在里面，AI 干活的过程看得见、管得住。
2. **它把"换模型"变成一件随时可做的事**——今天哪个模型好用、哪个更便宜、哪个必须留在本地，都可以按需切换，工作流不被任何一家厂商绑死。
3. **它把最敏感的东西留在了自己的电脑上**——代码、会话、录音、会议纪要、声纹、密钥，默认不出本机。

## 二、为什么需要它

### 2.1 三类现有方案的共同短板

过去两年，AI 辅助工作基本沿着三条路径发展，每条路径都解决了问题的一部分，也都留下了代价。

| 形态 | 典型代表 | 解决了什么 | 留下了什么代价 |
|---|---|---|---|
| 终端型 | 命令行 AI 编程助手 | 轻量、贴近开发习惯 | 交互密度低，长会话难读、改动难审、多任务难管 |
| IDE 内嵌型 | 编辑器内置 AI | 与代码上下文贴合 | 工作流被绑死在某个编辑器上，换工具即失效 |
| 云端 SaaS 型 | 网页版 AI 工作台 | 开箱即用、无需配置 | 代码与数据须经厂商中转，模型不可替换，停服即归零 |

一句话概括：**能力在增强，但用户的控制权在减弱。**

### 2.2 三个真实存在的代价

**代价一：数据主权。** 使用云端工具意味着企业的代码、需求、会议内容要离开自己的网络。对研发密集型企业，这不是偏好问题，而是合规与竞争问题。

**代价二：供应商锁定。** 模型能力每几个月就会重新洗牌。如果工作流与某一家模型深度绑定，那么"换一个更强的模型"这件事，会变成一次迁移工程，而不是一次配置修改。

**代价三：过程不可控。** 当 AI 能改代码、能执行命令时，"它能做什么"和"它被允许做什么"必须分开。缺少权限闸门的自动化，本质上是在赌运气。

### 2.3 本产品的应对思路

| 代价 | 应对 |
|---|---|
| 数据主权 | 本地优先：项目、会话、录音、纪要、密钥全部留在本机；无账号、无强制中转、无遥测 |
| 供应商锁定 | 模型可替换：任意兼容协议的服务、本地模型、自建网关都可接入，会话内即可切换 |
| 过程不可控 | 权限闸门：所有高权限操作须经独立的内核层判定，用户可逐次确认、可事后审阅 |

## 三、它是什么

### 3.1 能力全景

本产品不是单一功能，而是围绕"让 AI 长期、安全、可管理地干活"搭建的一整套桌面能力。

| 能力域 | 具体能力 | 对用户意味着什么 |
|---|---|---|
| 工作空间 | 项目打开、多会话、分支、归档、全文检索 | 像管理文件一样管理"和 AI 一起做过的事" |
| 工作模式 | Agent / Plan / Goal 三种授权边界 | 从"放手干"到"先批方案"到"只管结果"，按风险选择 |
| 模型接入 | 多家服务商、兼容接口、本地模型、自建网关 | 不被任何一家锁定，成本与能力可随时重配 |
| 工具执行 | 读文件、写文件、执行命令、搜索 | AI 能真正动手，而不是只给建议 |
| 权限管控 | 操作级别判定、逐次确认、会话级授权范围 | 高危动作必须过闸门，拒绝有记录 |
| 变更审阅 | 改动汇总、差异对比、命令输出 | 改了什么、为什么改，一屏看完 |
| 任务委派 | 子任务并行、独立上下文、结果回收 | 大任务拆开跑，主任务不被撑爆 |
| 扩展生态 | 插件、技能包、外部工具协议 | 核心保持克制，能力靠生态长出来 |
| 历史迁移 | 导入其它工具的本地会话 | 老工作不断档，迁移成本低 |
| 会议纪要 | 录音、转写、分人、总结、导出 Word | 会后 3 分钟出纪要，而不是 90 分钟 |

### 3.2 三种工作方式：把"授权"做成可选档位

这是本产品最容易被忽略、但对管理者最重要的设计。同一个 AI，可以提供三种完全不同的控制边界。

| | **Agent（放手干）** | **Plan（先批方案）** | **Goal（只管结果）** |
|---|---|---|---|
| 你需要确认什么 | 不需要额外确认 | 实施方案 | 目标与验收条件 |
| AI 会怎么做 | 读代码、改文件、跑命令、自测、继续迭代 | 先调研，产出冻结的方案，等你批准后才动手 | 自己选路径，持续推进到目标达成 |
| 适合什么场景 | 日常改动、明确的小任务 | 大型重构、高风险改造、重要功能 | 结果明确但路径不确定的任务 |
| 风险水平 | 中（靠权限闸门兜底） | 低（动手前有人把关） | 中高（需清晰验收标准） |

**设计要点：** 三种模式下，高权限操作仍然要过权限闸门。模式决定的是"要不要先审批方案"，不是"要不要受约束"。

### 3.3 与"又一个 AI 聊天框"的区别

| 维度 | 普通 AI 聊天工具 | 本产品 |
|---|---|---|
| 工作对象 | 一段对话 | 一个项目、一批文件、一串长期任务 |
| 记忆方式 | 关掉就忘 | 会话落盘、可检索、可恢复、可分支 |
| 动手能力 | 给建议 | 读写文件、执行命令、自检验证 |
| 安全边界 | 无（或只有对话框） | 独立内核层判定 + 审计留痕 |
| 生命周期 | 一次会话 | 连续数小时、跨多次重启 |
| 扩展方式 | 等厂商更新 | 插件、技能包、外部工具协议 |

## 四、技术逻辑：它是怎么搭起来的

这一章解释"为什么这样设计"。不需要技术背景也能读懂，关键看每个角色"负责什么、不负责什么"。

### 4.1 一个朴素的判断

绝大多数 AI 桌面工具的架构问题是同一个：**界面、智能、权限三件事混在一起。**

混在一起的后果很直接——界面代码能碰文件，智能逻辑能碰密钥，一个渲染错误可能导致数据被改。功能加得越快，风险积累得越快。

因此本产品在第一天就做了一个决定：**把这三件事分成四个彼此独立的角色，用明确的边界隔开。**

### 4.2 四个角色

```text
┌──────────────────────────────────────────────────────────┐
│  ① 前台（界面层）                                         │
│  会话、项目、审阅、设置、插件、会议纪要                     │
│  只能"看"和"请求"，不能直接碰文件和数据库                  │
└────────────────────────▲─────────────────────────────────┘
                         │ 受控请求（白名单）
┌────────────────────────┴─────────────────────────────────┐
│  ② 调度室（桌面主进程）                                   │
│  窗口与生命周期、请求转发、子进程监督、录音状态机、更新     │
│  只做协调，不做业务判断                                    │
└───────▲──────────────────────────────▲───────────────────┘
        │ 本地协议（不出本机）          │ 本地协议
┌───────┴──────────────────┐  ┌────────┴───────────────────┐
│  ③ 档案室 + 门卫（内核层）│◄►│  ④ 工程师（智能体运行时）  │
│  Rust 实现                │  │  模型调用、推理循环、流式   │
│  权限判定、文件操作、      │  │  上下文管理、任务委派       │
│  数据持久化、密钥、审计    │  └────────┬───────────────────┘
│  录音与转写存储、Word 生成 │           │ HTTPS（可配置）
└───────▲──────────────────┘           ▼
        │                    ┌──────────────────────────────┐
┌───────┴──────────────────┐ │  模型服务（用户自选）        │
│  ⑤ 语音处理（独立进程）  │ │  云端 / 本地 / 自建网关      │
│  语音识别、声纹、分人     │ └──────────────────────────────┘
└──────────────────────────┘
```

| 角色 | 技术实现 | 只做这些 | 明确不做这些 |
|---|---|---|---|
| ① 前台 | React + TypeScript | 展示、交互、发起请求 | 不读写文件、不连数据库、不持有密钥 |
| ② 调度室 | Electron 主进程 | 窗口、转发、监督进程、录音编排 | 不做权限判断、不做数据存取 |
| ③ 档案室 + 门卫 | Rust 独立进程 | 权限判定、文件读写、数据存取、密钥、审计、文档生成 | 不调用模型 |
| ④ 工程师 | Node 独立进程 | 模型调用、推理循环、上下文、委派 | 不直接写盘、不直接读密钥 |
| ⑤ 语音处理 | Rust 独立进程 | 语音识别、声纹提取、说话人聚类 | 不联网、不写数据库 |

### 4.3 这样切分带来三个好处

**好处一：权限无法被绕过。**
界面层发出的任何请求，都要经过调度室转给内核层，由内核层重新判定"这个操作在当前项目内是否允许"。界面层说自己要写某个路径，不等于它被允许写——判定权在内核层，参数不可信。这就是"门卫"的意义：**钥匙不在需要进门的那个角色手上。**

**好处二：一个环节出问题不会拖垮全局。**
界面卡住不影响录音；语音识别占用 CPU 不影响对话；智能体进程崩溃可以由调度室重启并从检查点恢复。四个角色各有各的崩溃边界，这是长时间连续可用的前提。

**好处三：加功能不必动核心。**
想加一个新面板、一个新工具、一个新主题，走插件通道；想加一个新能力域（比如会议纪要），按"界面展示 → 调度编排 → 内核持久化"的固定切分接入，不新增特殊通道。

### 4.4 为什么选这些技术

选型不是追新，而是被约束推出来的。

| 位置 | 选择 | 为什么 |
|---|---|---|
| 桌面外壳 | Electron | 三平台表现一致、生态成熟、能直接复用 Node 侧的智能体生态；项目复杂度在"协作与安全"，不在"界面渲染性能" |
| 特权内核 | Rust | 内存安全、单文件可执行、跨平台编译成熟；权限与数据这类"不能出错"的部分，值得用更严格的语言 |
| 智能体引擎 | 复用成熟开源框架 | 模型适配、流式输出、工具循环这些已被验证的能力不必重写，把预算放在差异化上 |
| 进程通信 | 本机管道 + 结构化消息 | 不占端口、天然进程绑定、无对外网络暴露面 |
| 数据存储 | 结构化索引库 + 追加式日志 | 长文本流式写入不抢锁，检索与关联查询走索引，兼顾两者 |
| 界面技术栈 | React + TypeScript | 类型安全、生态大、插件面板可动态挂载 |

**一句话：能被替换的都不写死，不能出错的都用最严的方案。**

## 五、六个技术支点

这六点是"为什么它值得长期用"的答案。

### 5.1 本地优先，但不玩文字游戏

"本地优先"常被滥用。本产品的定义是可核查的：

| 数据 | 存放位置 | 是否出本机 |
|---|---|---|
| 项目文件 | 用户自己的目录 | 否 |
| 会话记录 | 本机日志文件 + 本地索引库 | 否 |
| 设置 | 本机配置文件 | 否 |
| API 密钥 | 操作系统密钥库（Keychain / 凭据管理器） | 否 |
| 录音与转写 | 本机（项目目录或用户数据目录） | 否 |
| 会议纪要与 Word | 本机 | 否 |
| 声纹档案 | 本机，默认关闭 | 否 |
| 使用行为统计 | 不采集 | —— |
| 模型请求内容 | 直达用户自己配置的服务商 | 取决于用户选择的模型服务 |

**关键澄清：** 本地优先不等于"永远不联网"。使用远程模型时，对话内容必然要发给那家模型服务商，这一点由用户选择决定，产品不做隐瞒。产品承诺的是：**没有中间商，没有额外中转，没有偷偷上报。**

### 5.2 模型是可替换零件

产品不维护"官方指定模型清单"。可选范围包括：主流云服务商、兼容协议接口、本地推理服务、企业自建网关。每个模型可独立配置上下文长度、输出上限、推理强度、温度等参数，并且**在同一个会话里就能切换**，不需要重建会话、不需要迁移历史。

对管理者的意义：模型能力每几个月洗牌一次，企业不必因为"更强的模型出现了"而做一次迁移工程；对成本敏感的任务可以走低价模型，对质量敏感的任务可以切高价模型，对涉密内容可以只用本地模型。

### 5.3 权限闸门：能干活，但不乱来

AI 要真正干活，必须能改文件、能跑命令。这正是风险所在，因此产品把权限做成了独立的一层，而不是散落在各处的判断。

| 环节 | 机制 |
|---|---|
| 范围限定 | 所有文件操作限定在本次会话绑定的项目目录内；越界直接拒绝 |
| 路径校验 | 规范化 → 越界判断 → 敏感目录拦截 → 留痕，四步之后才执行 |
| 风险分级 | 读操作、写操作、执行命令、删除操作，风险等级不同，处理方式不同 |
| 逐次确认 | 高权限操作弹出确认卡片，展示完整参数；用户可拒绝并附理由 |
| 超时默认拒绝 | 无人响应时判定为拒绝，而不是默认放行 |
| 记忆边界 | 允许"本会话内同类操作不再询问"，但不得跨会话继承 |
| 审计 | 写盘、执行、授权、导出、声纹操作全部留痕，可导出核查 |

**设计原则：默认拒绝，显式授权。** 宁可多问一次，不可默认放行。

### 5.4 为长任务而设计

大多数 AI 工具擅长一问一答。真正的工作往往要跑半小时、一小时，甚至跨几次重启。产品围绕"长任务"做了三件事：

1. **过程可恢复**：流式输出过程中持续写入检查点；应用重启后恢复现场，中断的轮次标记为"已中断"而不是静默重放。
2. **上下文可管理**：接近上限时对早期过程做摘要压缩，保留结论与决策，丢掉冗余过程；项目规范文件长期注入，不占对话预算。
3. **任务可拆分**：把独立子任务委派给独立上下文的子任务执行者，主任务只收结构化结果。大仓库探索、多文件实现、独立复核都可以并行推进。

### 5.5 核心克制，能力外置

产品的长期风险不是功能不够，而是"什么都内置"导致越来越重、越来越难维护、越来越难审计。

因此扩展能力被设计成多层，从轻到重：

| 层级 | 形式 | 适合做什么 |
|---|---|---|
| 最轻 | 技能包（可复用的提示词与流程） | 沉淀团队规范、固定工作流 |
| 中 | 外部工具协议（MCP） | 接入已有系统与工具服务 |
| 中 | 插件 | 增加工具、命令、面板、视图、主题 |
| 较重 | 常驻服务插件 | 后台长期运行的能力 |

插件有独立的清单规范、权限声明与进程隔离，越权调用会被拒绝并记录。同时产品明确告知用户：**插件属于用户主动信任的代码，不是操作系统级沙箱**——这句话看似是免责，实则是对风险边界的诚实交代。

### 5.6 三平台同一套体验

Windows、macOS、Linux 均有安装包，功能一致。这看起来是工程细节，实际是组织价值：一个团队里有人用 Mac、有人用 Windows，工具不统一就意味着经验无法沉淀、规范无法统一执行。

## 六、新增能力：会议纪要生成

> **阶段说明：** 本章描述的是已规划的下一阶段能力，与现有工作台复用同一套模型配置、权限体系与数据规范，当前版本尚不包含。此处完整说明设计意图与业务价值，供决策评估。

### 6.1 一个所有人都熟悉的场景

会议结束后，通常发生这几件事：

- 有人要花 60–90 分钟回听录音、整理文字；
- 整理出来的纪要靠回忆补全，人名、数字容易出错；
- 待办事项散落在不同人的笔记里，一两周后无人跟进；
- 录音文件存在某个人的手机里，事后既找不到、也不敢删。

**会议是组织里信息密度最高的场合，也是信息流失最严重的场合。**

### 6.2 产品化的解决方式

在会议现场打开本产品，点击"会议记录"，之后是五步：

```text
① 录音      一键开始，实时显示时长与输入电平
     ↓
② 转写      边说边出字，会后整段重算以提升准确率
     ↓
③ 分人      自动区分"谁在说"，可一键改名、合并、拆分
     ↓
④ 总结      按模板生成结构化纪要：议题、要点、结论、待办、责任人
     ↓
⑤ 导出      生成 .docx 文档，可直接分发或归档
```

| 步骤 | 用户看到什么 | 背后发生了什么 |
|---|---|---|
| 录音 | 波形、计时、"正在录音"提示 | 麦克风采集 → 标准化音频 → 每 5 分钟分片落盘（异常也不丢） |
| 转写 | 字幕滚动 | 本地语音识别模型推理，不上传任何音频 |
| 分人 | "发言人 1/2/3" | 提取声纹特征 → 会议内聚类 → 与时间轴对齐 |
| 总结 | 按模板填好的纪要草稿 | 分块归纳 → 汇总去重 → 按模板字段结构化输出 → 完整性校验 |
| 导出 | Word 文件 | 内核层生成文档 → 校验 → 原子写入 → 记录导出路径 |

### 6.3 三个关键设计决策

**决策一：语音识别全部在本机完成。**

音频是最敏感的数据之一，它包含说话内容、语气、甚至情绪。把录音上传到云端转写，等于把会议室搬到了别人的服务器上。因此本模块采用本地识别：模型首次使用时下载到本机，之后完全离线可用。

代价也要说清楚：本地模型准确率略低于顶级云端服务，且需要占用磁盘（数百 MB 至 1 GB 级）与 CPU。产品通过"两档模型 + 术语表 + 会后整段重算"来弥补，用户可根据设备性能选择。

**决策二：只录麦克风，不录系统声音。**

现场会议用麦克风即可满足需求。采集系统播放声音需要操作系统级的特殊通道，Windows 与 macOS 实现差异大、稳定性差、权限申请复杂，且与"只记录现场发言"的用途不匹配。因此首版明确不做，避免为了一个边缘场景牺牲整体稳定性。

**决策三：说话人识别以"可用"为先，以"可纠正"为底。**

自动区分说话人这件事，在两人对话中表现良好，在多人抢话、口音重、麦克风远场时会退化。与其承诺"百分百准确"，不如把设计重点放在**人工纠正的成本**上：

- 自动给出"发言人 1/2/3"，并显示每人发言时长与占比；
- 改名一次，全文同步；
- 合并、拆分一键完成；
- 短句采用时间邻近推断，减少"同一人被拆成两个"的碎片。

同时提供**跨会议声纹库**作为增强能力：为固定参会人建立声纹档案后，下次会议可自动认人并标注置信度。该能力默认关闭，档案仅存本机，删除即物理清除。

### 6.4 模板：让纪要符合组织习惯

不同会议的纪要结构不一样。产品内置三类模板，也允许自定义：

| 模板 | 结构 |
|---|---|
| 决策型 | 会议信息 → 背景 → 议题与讨论 → 结论与决议 → 待办事项 → 风险与遗留 |
| 周会型 | 会议信息 → 本周进展 → 问题与阻塞 → 下周计划 → 待办事项 |
| 访谈型 | 会议信息 → 受访者背景 → 核心观点 → 引用要点 → 结论与后续 |

模板不只是"格式"，它同时约束了总结的**提问方式**：要求模型按章节取信息，比让它"随便总结一下"要稳定得多。

### 6.5 一条不能突破的底线：不编造

AI 总结最大的风险不是写得不好，而是**写得像真的**。

本模块在设计上做了四道约束：

1. **信息不足时显式标注"未提及"**，不允许推测人名、数字、结论。
2. **结论与待办可溯源**：每条要点能点回原文对应的时间段。
3. **说话人使用确认后的真实姓名**，不使用"发言人 1"这类占位标签进入正式文档。
4. **输出结构化校验**：必填字段缺失会被列出，提示人工补充，而不是用空话填满。

**给管理者的判断依据：** 一份"承认自己不知道"的纪要，比一份"通篇流利但人名全错"的纪要安全得多。

### 6.6 降级路径：坏情况下依然可用

| 故障 | 处理 |
|---|---|
| 语音模型未安装 | 先录音，会后补装模型再处理，录音不丢 |
| 模型服务不可用 | 输出纯转写版纪要（含分人与时间轴），仍可导出 Word |
| 录音中设备断开 | 自动切换默认设备，缺口在时间轴标记 |
| 录制中应用崩溃 | 已落盘分片保留，重启后继续处理 |
| 磁盘不足 | 停止录制，保留已有数据并提示 |

### 6.7 与"录音笔 + 人工整理"的对比

| 维度 | 现状做法 | 本模块 |
|---|---|---|
| 纪要产出时间 | 会后 60–90 分钟 | 会后 3 分钟内出草稿，10 分钟内定稿 |
| 信息完整度 | 依赖记录者记忆与手速 | 全文可回溯，要点可溯源 |
| 待办跟进 | 靠人盯 | 结构化待办（事项/责任人/期限/状态） |
| 数据安全 | 录音存在个人手机或网盘 | 全部留在本机，可随项目统一清理 |
| 复用价值 | 一次性 | 沉淀为可检索的组织知识 |

### 6.8 合规提示

录音涉及他人权益。产品在首次使用前要求确认知情提示，录制过程中界面常驻可见指示，并在文案中明确：**取得参会人同意是使用者的责任。** 产品不提供隐蔽录音能力。

## 七、价值分析

### 7.1 价值从哪里来：四个可核算的方向

产品价值不来自"用了 AI"这件事本身，而来自四个可核算的改善方向。以下每一条都给出**测算口径**，便于按本组织实际参数代入。

| 方向 | 价值来源 | 测算口径 |
|---|---|---|
| 效率 | 重复性、低创造性劳动被压缩 | 单次任务节省时长 × 频次 × 涉及人数 |
| 成本 | 模型可按任务分层使用 | 任务量 × 单位成本差异 |
| 风险 | 数据不出域、操作可审计 | 事件概率 × 单次损失（风险规避口径） |
| 资产 | 过程与结论沉淀为可复用知识 | 可检索条目数 × 复用次数 |

### 7.2 效率价值：以会议纪要为例的测算模型

会议纪要是最容易算清账的场景，因为它有明确的人工基线。

**测算模型：**

```text
周节省人时 = 周会议场次 × 需产出纪要比例 × (人工整理时长 − 工具处理时长)
年节省人时 = 周节省人时 × 有效工作周数
```

**代入示例（参数可替换）：**

| 参数 | 取值 | 说明 |
|---|---|---|
| 周会议场次 | 10 场 | 中等规模研发团队 |
| 每场时长 | 1 小时 | —— |
| 需产出正式纪要的场次 | 6 场/周 | 并非所有会议都需要正式纪要 |
| 人工整理时长 | 70 分钟/场 | 回听 + 整理 + 校对 |
| 工具处理时长 | 13 分钟/场 | 3 分钟自动生成 + 10 分钟人工审核修改 |
| 有效工作周 | 45 周/年 | 扣除假期 |

**结果：** 单场节省约 57 分钟；按 6 场/周计，约 **5.7 小时/周**，全年约 **256 人时**。

这个数字的意义不在精确，而在于**它可被验证**：试点一个月后，用实际会议记录与人工耗时对照，即可校准参数。

**附带收益（难以量化但可感知）：**

- 纪要产出从"会后一天"提前到"会后十分钟"，决策传导速度变快；
- 待办事项从"口头交代"变成"结构化清单"，跟进不再依赖个人记忆；
- 因记录者缺席而无法成会的约束消失。

### 7.3 成本价值：让每个任务用合适的模型

AI 使用成本的核心矛盾是：**能力最强的模型最贵，而大量日常任务并不需要最强模型。**

本产品把"换模型"的成本降到一次点击：

| 任务类型 | 建议模型档位 | 效果 |
|---|---|---|
| 简单改写、格式整理、单文件小改 | 轻量/低价模型或本地模型 | 成本显著下降，质量足够 |
| 常规开发、代码理解、文档生成 | 中档模型 | 质量与成本平衡 |
| 架构设计、复杂重构、疑难排查 | 旗舰模型 | 保证结果质量 |
| 涉密内容的处理 | 本地部署模型 | 零外发，成本仅为硬件折旧与电费 |

**对采购的意义：** 不需要为"所有人所有任务"采购同一档旗舰模型额度，也不需要把预算锁死在某一家。模型价格变动时，只需调整配置，不必变更工具链。

> 说明：模型调用费用由用户与服务商直接结算，本产品不内置额度、不做二次计费、不抽取中间费用。

### 7.4 风险与合规价值

这是最容易被低估、但在评审会上最有分量的一条。

| 风险类型 | 传统云端方案的暴露面 | 本产品的处置 |
|---|---|---|
| 源代码外泄 | 代码需上传至服务商 | 代码不出本机；仅将必要的对话上下文发给用户指定的服务商 |
| 会议内容外泄 | 录音上传云端转写 | 音频全程本地处理，不上传 |
| 凭证管理不当 | 密钥常以明文存在配置里 | 密钥存于操作系统密钥库，界面不可见完整值 |
| AI 误操作 | 无权限约束，出错即造成损失 | 越界拒绝、逐次确认、超时默认拒绝 |
| 事后无法追责 | 无操作记录 | 写盘、执行、授权、导出全程留痕，可导出核查 |
| 供应商停服 | 服务终止即无法使用 | 工具本体不依赖单一服务商，可切换端点继续工作 |

**一句话表述：** 它把"AI 带来的效率"与"AI 带来的暴露面"分开处理——效率最大化，暴露面最小化。

### 7.5 资产价值：把过程变成可复用的组织知识

大部分 AI 工具的价值在对话结束时就消失了。本产品把三样东西留了下来：

1. **会话资产**：历史会话可全文检索、可分支、可恢复。三个月前那次排查的思路，今天还能找回来。
2. **纪要资产**：会议纪要与原始转写共同保存，结论可溯源到原话，避免"纪要怎么说"与"会上怎么说"两张皮。
3. **方法资产**：把团队规范、检查清单、固定流程做成技能包，一次沉淀、长期复用，新人上手不必口口相传。

组织能力往往不是缺信息，而是**信息留不下来、找不到、用不上**。这三类资产直接对应这三个问题。

### 7.6 战略价值：不被锁死

| 锁定维度 | 传统方案的锁定方式 | 本产品的应对 |
|---|---|---|
| 模型锁定 | 绑定单一厂商，换模型等于换工具 | 模型可替换，会话内切换 |
| 数据锁定 | 数据在厂商侧，导出受限 | 数据在本机，格式开放 |
| 工作流锁定 | 绑定特定编辑器或终端 | 独立桌面应用，编辑器随意 |
| 生态锁定 | 能力只能等厂商更新 | 插件与外部工具协议，自主扩展 |

对组织的长期意义：**工具选型可以随技术变化调整，而资产与流程不必推倒重来。**

## 八、与同类方案的定位对比

| 维度 | 终端型 AI 助手 | IDE 内嵌型 | 云端 AI 工作台 | **本产品** |
|---|---|---|---|---|
| 数据位置 | 本机 | 本机 | 厂商侧 | **本机** |
| 模型自由度 | 中 | 中 | 低 | **高（可接任意兼容端点）** |
| 长会话与审阅 | 弱（纯文本流） | 中 | 中 | **强（工作台视图 + 差异对比）** |
| 权限管控 | 弱（提示确认为主） | 弱 | 中（平台侧） | **强（独立内核层判定）** |
| 长期任务恢复 | 弱 | 中 | 中 | **强（检查点 + 现场恢复）** |
| 扩展能力 | 中 | 中 | 低 | **强（插件 + 工具协议 + 技能包）** |
| 会议纪要 | 无 | 无 | 有（需上传） | **有（全本地，规划中）** |
| 团队统一部署 | 中 | 受编辑器制约 | 易 | **易（三平台一致）** |

**差异化结论：** 同类产品大多在"某一维度做到极致"，本产品的取向是**在关键维度上都不妥协**——数据留在本地、模型可换、权限可控、任务能长跑、能力可扩展。代价是工程复杂度更高，这正是一套分层架构要解决的问题。

## 九、落地路径

采用"分段可交付"策略，每一阶段结束都有可独立使用的成果，避免一次性大投入。

| 阶段 | 内容 | 交付物 | 用户可感知的成果 |
|---|---|---|---|
| 阶段一（已具备） | 桌面工作台核心：项目/会话、三种模式、多模型接入、权限与审阅、任务委派、插件生态、跨平台打包 | 三平台安装包 | 可以在本机用 AI 完成真实开发任务 |
| 阶段二（规划） | 会议纪要：录音与音频管线、本地转写、说话人分人与校正、模板、AI 总结、Word 导出 | 会议模块 + 纪要模板 | 会后 3 分钟出纪要草稿 |
| 阶段三（规划） | 团队化：受控本地接口、团队模板库、声纹档案管理、纪要共享与归档规范 | 团队配置包 | 同一套规范在团队内统一执行 |

**推进建议：**

1. **先小范围试点**：选 1 个团队、10–20 人，跑一个月的会议纪要，用第 7.2 节的模型校准真实节省值。
2. **先解决"最痛的一场会"**：从周会或决策会开始，而不是全部会议铺开，降低使用习惯改变的成本。
3. **先定规范再推广**：模板、命名规则、归档位置在试点期定下来，推广时才不会各写各的。

## 十、风险与边界（如实说明）

一份可信的介绍文档，必须把限制写清楚。

| 事项 | 现状 / 限制 | 影响 | 应对 |
|---|---|---|---|
| 成熟度 | 处于早期预览阶段，接口与部分桌面行为仍在演进 | 大规模推广前建议先试点 | 分段交付，关键接口冻结后再扩大范围 |
| 本地语音识别精度 | 略低于顶级云端服务；对远场、重口音、强噪声敏感 | 关键会议仍需人工校对 | 两档模型可选、支持术语表、会后整段重算、保留人工编辑 |
| 设备要求 | 实时转写依赖 CPU 性能；模型占用数百 MB 至 1 GB 磁盘 | 老旧设备体验下降 | 可关闭实时字幕，仅保留会后处理 |
| 说话人分离 | 多人抢话、短发言场景准确率下降 | 需人工纠正 | 以"易纠正"为设计目标，提供改名/合并/拆分 |
| 插件安全 | 插件属于用户主动信任的代码，非操作系统级沙箱 | 安装恶意插件有风险 | 权限声明、进程隔离、越权拒绝、只安装可信来源 |
| 录音合规 | 录音涉及参会人权益 | 存在合规风险 | 知情提示、录制指示常驻、明确使用者责任、不提供隐蔽录音 |
| 模型费用 | 由用户与服务商直接结算 | 用量大时成本上升 | 支持分层用模型与本地模型 |
| 会议模块 | 尚在规划阶段，当前版本不含 | 不能立即使用 | 按第九节阶段二推进 |

**不做的事（明确排除）：**

- 不做账号体系与强制云端同步；
- 不做强制中转网关；
- 不做系统播放音频采集；
- 不做云端语音转写；
- 不做隐蔽录音；
- 不做多人实时协同编辑。

## 十一、结语

如果把这件事压缩成三句话：

1. **对使用者**：它是一个能真正干活的 AI 工作台——项目在里面，改动看得见，长任务跑得住，模型随时换。
2. **对管理者**：它是一个可控的 AI 入口——数据留在自己手里，高危操作有闸门，过程可审计，成本可分层。
3. **对组织**：它是一台把"每次协作"沉淀为"组织资产"的机器——会话可检索、纪要可溯源、方法可复用。

技术上的取舍可以概括为一句：**能被替换的都不写死，不能出错的都用最严的方案，能外置的都交给生态。**
