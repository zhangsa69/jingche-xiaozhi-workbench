## 0.5 本期附加：限流自动重试（不在 W-01…W-40 内）

用户反馈：provider 触发 limit 后，runtime 的十次预算一耗尽就停在错误行，必须手点重试，而手点通常一次就成功。本期把这一次点击交给程序完成。

- **runtime 的预算不变**：十次、退避与 abort 语义仍按 ADR 0206。本轮只修分类——`402`、以及正文带 quota / limit / capacity 措辞的 `403`，归 `PROVIDER_RATE_LIMITED`（此前 403 一律判 `PROVIDER_UNAUTHORIZED` 且不可重试，正是这些网关的实际形态）；关键词扩到 `usage limit` / `limit reached` / `insufficient_quota` / `resource_exhausted` / `请求过于频繁`。上下文模式先判，`token limit exceeded` 仍是 `CONTEXT_TOO_LARGE`，不会把「提示词太长」当限流重试。
- **渲染端续轮**：预算耗尽后最多再发 3 轮，间隔 30s / 90s / 180s。只对可重试码生效，只对当前会话；发射前复核「没有 turn 在跑、会话没切、末条仍是同一错误码」，任一变化即静默放弃，不会在用户已经走开时补发请求。
- **轮次计数放在模块作用域**，不进 store：新一轮开始时会清掉 store 里的倒计时（错误行已经消失），若计数也随之清空，三次就会变成无限循环。
- **可见与可退**：错误卡片显示倒计时、立即重试、取消自动重试；另补一个普通「重试」按钮——此前可重试错误没有任何一键恢复入口。
- 落点：`packages/agent-runtime/src/agent-errors.ts`、`apps/desktop/src/lib/auto-retry.ts`、`stores/slices/auto-retry-slice.ts`、`stores/slices/events-slice.ts`、`features/chat/transcript/shared.tsx`、`styles/messages.css`、8 语言 `chat.autoRetry*` / `chat.retryResponse`
- 验证：`apps/desktop/test/auto-retry.test.mjs`（7 例）、`packages/agent-runtime/src/agent-errors.test.ts` 增 3 例（合计 23）；三项变异自检按预期变红并已还原（可重试码集合失效 2 红、退避序列改截断 1 红、去掉 403 配额判定 1 红）
- 边界：不无限重试；不自动重试鉴权失败、上下文溢出与用户主动 Stop；每轮都是新请求，会产生 token 成本
- 决策记录：`docs/adr/0210-renderer-auto-retry-after-budget.md`

### W-04 循环执行确认 ✅

同工具、同参数、**同结果**的第 3 次调用不再静默终止，而是停下来问「继续 / 停止」。

### W-14 导出 / 另存 ✅

产物能看见了，现在也能取走：预览页与产物行各有一个「另存为」，弹出系统保存对话框。

- **改了计划里的口径，理由写在代码里**：原计划要 `fsWrite` + `artifactExport` 两条。只做一条 `fs/export`。`fsWrite` 会让 renderer 指定写盘目标，等于在「改动必留审阅记录、可回滚」的证据链上开一个后门；导出是单向的——源必须已在授权根内（复用 `fs/reveal` 的 `resolveRealOpenablePath`），目标由系统对话框返回，renderer 全程说不了目标路径。于是 `fs/export` 相较读盘**零新增权限**：一个本来就能打开的文件，被放到用户自己选的地方。
- **`sanitizeExportName` 是唯一能在 renderer 影响默认文件名的入口**，所以它只产出裸文件名：分隔符与保留字符折成 `-`，`.`/`..` 归空，长度截到 120。

### W-13 PDF 生成 ✅

`/pdf` 或命令面板「导出任务为 PDF」：当前会话 → PDF → 保存对话框，一步到位。

- **渲染在谁手里是分清的**：renderer 负责文档长什么样（Markdown 用与面板同一个 `marked` 解析器转 HTML），主进程负责窗口和文件。这样页面上没有任何脚本能自己够到网络或磁盘，也不必让主进程理解 Markdown。
- **窗口是消耗品**：`show: false` + `sandbox` + 无 node，`loadFile` 后 `printToPDF`，`finally` 里 `destroy()` 并删掉中间 HTML。中间文件用点号开头写在目标旁边，Chromium 只肯打印自己加载的文件，除此之外没有多余状态。
- **落在 scratch，让导出继续走 `fs/export`**：PDF 不是新的写盘通道，而是先落进文件面板本来就能读的 scratch 目录，再由 W-14 那条通道弹保存框。两条通道各自只做一件事。

### W-17 运行日志面板 ✅

工作面板新增「日志」标签：把应用自己写下的 NDJSON 读回来，可切通道、按级别过滤、搜索、跟随尾部。

- **读文件，不新增推送通道**：日志本来就是落盘的 NDJSON（`<data_dir>/logs/<channel>/<category>.log`），缺的只是一个读回它的入口。`log/tail` 只读，渲染器拿到的结构和写盘那份同源，不维护第二套日志模型。
- **只读尾部窗口**：每个文件按 256 KiB 从末尾读，先丢掉窗口首行的残片（窗口几乎总是从行中间开始），再丢掉解析不了的行。这样被 kill 掉的写入进程留下的半行不会连带遮蔽它前面的整份日志——这正是「崩溃后第一件想做的事」。
- **轮转文件不混进来**：只认 `<category>.log`，`*.N.log` 是面板没索要的历史；真截断了由 `truncated` 说明，而不是拿一堆旧行冒充当前状态。
- **未知通道 / 级别报错而不是给空列表**：`sanitizeLogRequest` 对不在 `app|host|agent`、`debug|info|warn|error` 里的值抛 `INVALID_ARGUMENT`。空列表会被读成「没有日志」，这比报错更容易误导人。
- **过滤与计数留在渲染端**：`filterLogRecords` / `logLevelCounts` 是纯函数，输入、改级别、改搜索词都不走 IPC；主进程只负责「给我最新的 N 行」。级别过滤在主进程也做了一次（先过滤再截断），否则 `limit` 会把目标级别的行挤出去。
- **轮询 2s 而不是订阅**：host 通道的日志由另一个进程写文件，订阅最终还是要轮询一个文件，只会多一层机制。2 秒比人读得快。
- **截断必须可见**：窗口裁掉字节或匹配行数多于 `limit` 时面板明说「只显示最近 N 条」，避免「以为看到了全部」。

### W-19 富格式预览 ✅

文件面板里点开 `.docx` / `.xlsx` / `.pptx` 直接看到内容，不再是「二进制无法预览」。方案原稿的路子是「转 HTML 交内嵌浏览器（mammoth / SheetJS）」，这里改成**主进程解析成结构化 JSON、渲染端用 React 画**。

- **为什么不转 HTML**：`mammoth` / SheetJS 都不在仓库里，也没有离线包；而且把文档转成 HTML 再塞进 `BrowserPreview`，等于把解析结果当不可信标记语言渲染，`<img onerror>` 一类注入要另做一层清洗。现在解析器只产出 `string[][]` 与纯文本块，渲染端是 `<table>` / `<p>` / `<li>`，**没有一处 `dangerouslySetInnerHTML`**。
- **零依赖自写 ZIP + XML**：容器支持 method 0（store）与 method 8（deflate，`zlib.inflateRawSync`），从 EOCD 反向找中央目录、逐条校验大小与中央目录一致；XML 用局部名匹配（`w:p` → `p`），容忍命名空间前缀变化。**必须支持 `xl/sharedStrings.xml`**——真实 Excel 存的都是共享字符串表，只有我们自己 `pi.office` 的产物是 `inlineStr`，两条路径都有测试（这正是「生成器能打开、真实文件打不开」的典型坑）。

- **上限与截断明说**：文件 16 MiB、块 2000、表行 200、sheet 20、sheet 行 500、列 64、页 200、单块 5000 字符，以及**总格数 5 万**（所有表格与 sheet 共用一个预算：按表的上限会相乘，2000 块 × 200 行远超面板能挂载的量，而渲染端不自行截断——它只画宿主返回的内容，截断只能由宿主标注）。任一超限置 `truncated: true` 由界面提示，**不抛错**；zip 损坏、缺 `word/document.xml` → `unsupported/corrupt`，渲染端回落到「用系统默认程序打开」，不给用户看白屏或半张表。

- **过滤规则可测**：`/v1/models` 会把 embedding、whisper、tts 一起列出来，若照单全收，默认模型选择器里就会出现一选就失败的条目。`isChatModelId` 在探测阶段丢弃它们；去重按大小写不敏感、保留运行时返回顺序。
- **上下文窗口保守取值**：本地运行时常常不报 limits，`bindingFromModelInfo` 会落到云默认 128k，导致 agent 迟迟不压缩。未公布时改用 32768 / 4096。

### W-18 任务历史与重跑 ✅

### W-20 首次授权引导（文件夹说明）✅

空态新增一张说明卡：在用户第一次于某个文件夹开工前，用三行讲清产物写到哪里、读越界会先问、哪些数据只留本机。

- **不做目录级 trust**：现有授权是「会话 + 工具名」粒度（`session_grants`），再叠一层目录授权只会让两套规则互相解释不清。说明卡只解释既有规则，不新增闸门——发送按钮的行为一个字都没变。
- **三行的顺序按用户真实疑问排**：先「写到哪」（决定敢不敢按发送），再「读的范围」（决定放不放私密文件），最后「什么留在本机」（与隐私页同一口径）。写在前，是刻意与被问到的频次对齐。
- **关闭按文件夹记忆**：`workspaceGrantKey` 把路径归一化并统一大小写，`E:\work` 与 `e:/work/` 不会各问一次；记忆落在 `localStorage`，不新增 IPC，也不写进会话库。
- **没有文件夹时才给选择按钮**：`needsFolder` 派生自路径是否存在，而不是「用户是否第一次用」，因此已绑定文件夹的空态不会多出一个多余按钮；点击走与项目切换器同一条 `openProject()` + `newSession({ projectPath })` 路径。

### W-22 模板体系（目录 + 变量 + 批量套用）✅

新增「模板」页：左侧按文档 / 表格 / 幻灯片分组，右侧是变量表单，下方先给填好的全文预览，再谈插入。

- **预览就是将要发送的文本**：`applyTemplate` 返回的 `blocks` 直接渲染成预览，不做第二套拼装；因此预览里看到少一个字段，发送时也确实少。
- **一次报全所有缺失**：`missing` 收集全部必填空缺而不是遇错即停，表单不会出现「每次提交只红一个字段」的来回。

### W-27 提示词库（收藏 / 标签 / ↑ 历史召回）✅

- **发出即收录，命令除外**：只有真正发出去的可见文本入库；`/model` 这类斜杠命令不收，因为把命令当散文重发什么也不会发生。带 chip 的草稿先剥掉占位符再入库存，否则召回出来是一串哨兵字符。

- **↑ 只在空输入框生效**：有内容时 ↑ 仍归光标与自动补全菜单，多行草稿的常规操作不能被抢。

## 6. 已知债务与口径偏差

1. **W-08 的看门狗在 renderer 内**，没有 `electron/main/runtime/watchdog.ts`。三档语义等价（单调升档 → 每档只播一次），但「应用在后台时是否也计时」取决于窗口是否被节流，未做专门验证。
2. **W-05 不落库**（有意为之）：方案原写改 Rust plans 表，实际用「快照 + 工具行重放」。收益是不加迁移、重启天然一致；代价是步骤只在**批准过的计划**里存在，普通 agent 会话没有步骤条（这符合预期）。
3. **W-10 后台会话进度可能滞后**：会话切走后 pane 保留的是最后画面，侧栏显示会停住，切回即校正。要彻底实时，需要把 `UpdateStep` 事件按 sessionId 投影进 store，属于新增第二份状态，暂不做。
4. **W-03 落点在顶栏**而非 `transcript/`，§11 已注明。
5. **W-34 未按方案重做**：既有 MCP 市场已覆盖大部分需求，建议先做一次体验走查再决定是否补工。
6. **W-04 复用 asktool 通道**，没有新增「待确认事件」，确认条也不在 `ToolRow` 而在 `AskToolCard`。副作用是这条提问会出现在 asktool 的队列里（`queued` 计数会 +1）；语义上它确实是一次「需要人回答的往返」，但若后续要让两者在 UI 上彻底分开，需要给 `asktool_request` 加一个 `kind` 字段。
6b. **W-12 的产物不进「产物」标签**：产物标签读的是 `Write`/`Edit` 的 review 记录，插件用 `fs.writeBase64` 写的 docx/xlsx/pptx 不产生 review 记录。当前靠工具返回值里的路径让聊天渲染文件链接；要让它们出现在产物标签里，得给 review 记录补一条「插件写入」来源，属于 W-19 之后的口径问题。
6c. **W-19 的观感已量过一轮，剩两处要人眼 + 一处要设计决策**（详见 §5.1）：长表横滚（716/354、单滚动条）、16:9 比例（0.562）在真实产物 CSS 上通过；但**表格边框 2.19:1 低于 WCAG 1.4.11 的 3:1**，**骨架条 1.17:1（停格 1.05:1）在浅色纸上几乎看不见**。纸面刻意保持浅色、不随深色主题反转，所以这两个数字在两种主题下相同——要不要提对比度是视觉基线的事，本轮只记录不改。
6d. **`@pi-desktop/shared` 的 `dist` 不提交**：新增 `preview.ts` 后必须先 `pnpm -C packages/shared build`，否则桌面端 `typecheck` 会报「`@pi-desktop/shared` has no exported member `DocumentPreviewResult`」，运行时 `IPC.invoke.documentPreview` 也会是 `undefined`。这不是缺陷，是「包产物不入库」的固有代价，但第一次踩到时会像类型写错。
6e. **预览的格式灰区**：只认 `.docx` / `.xlsx` / `.pptx` 三个后缀，宏启用版本（`.docm` / `.xlsm` / `.pptm`，结构与前者完全相同）和老二进制格式（`.doc` / `.xls` / `.ppt`）都回落成 `unsupported/extension`——用户很可能把前者当 bug。另外 zip64、加密文档（CFB 容器）、合并单元格、xlsx 日期序列号（不读 `numFmt`，显示成 `45678`）、RTL 文本都未处理：前两者判 `corrupt`，后两者按原样呈现。
6f. **W-15 只覆盖 run 类工具**：面板只收 `action === "run"`（Bash / shell / exec），Read / Write / Grep 不进来——它们不是「命令输出」。命令原文取自 `tool_start` 参数，宿主自己截断过的输出在面板里也看不到全量，只能回对话查；这是刻意的，面板不做第二份输出缓存。
6g. **W-15 的裁剪阈值是常量**：`TERMINAL_ENTRY_CHARS = 8000` 单条从头部裁，整会话不做条数上限。极端会话（上千条命令）首次渲染会偏慢，届时正确的解法是虚拟列表而不是再分页（分页与 pinned-follow 冲突，见 §1 W-15）。
7. **提交状态**：M1、M2 的实现与文档已分别落在 `4f9634b0`（P0 功能）与后续 docs 提交中，W-04 单独提交。W-15 分两次：`35af602a`（实现 + 测试 + i18n）与本次 docs 提交；工作区干净。
