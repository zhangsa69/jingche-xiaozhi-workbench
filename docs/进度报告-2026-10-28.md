### W-04 循环执行确认 ✅

同工具、同参数、**同结果**的第 3 次调用不再静默终止，而是停下来问「继续 / 停止」。

- **判重指纹**：`repeatCallKey(toolName, params)` 做键排序与长字符串截断（200 字符），`Map` 上限 64 条；命中键之后还要比对结果指纹（`ok|text.slice(0,400)`）。结果一变就清零——「同一处反复改、每次都有新报错」属于正常排查，不该被拦。
- **挂起点在写锁之外**：包装器先 `await pauseRepeatedCall(...)`，用户不放行就不进入工具实现，因此不会和写锁、mutation failure budget 交叉。
- **复用 asktool 通道，零新增协议**：`waitForAskTool(signal)` 阻塞 → `asktool_request` 事件 → `AskToolCard` → `resolveAskTool(resolve)` 返回。问题文本用哨兵 `@@repeat-guard@@<tool>|<count>` 传递（`packages/shared/src/repeat-guard.ts` 两端共用），renderer 侧翻成 8 语言文案；`resolveRepeatGuardDecision` 把「关闭窗口 / 无答案」一律当 `stop`。
- **`continue` 要顺带清预算**：放行后调 `resetMutationBudget(...)`，否则同一次调用会被 mutation failure budget 立刻再杀一遍——这是实现时实测到的坑，已由 `runs the third identical call after the user chooses to continue` 固定下来。
- **`stop` 走错误收轮**：`details.errorCode = "REPEAT_CALL_STOPPED"`，`reportRepeatTermination` 在 `reportMutationTermination` 之后、`agent_end` 之前发 `error`，避免界面停在「正在思考」。
- **卡片形态**：guard 模式下 `AskToolCard` 隐藏进度、指示点、全部拒绝、跳过、下一步与自定义输入，只留两个一键决策按钮；标题/问题/按钮文案全部来自 locale。

### W-14 导出 / 另存 ✅

产物能看见了，现在也能取走：预览页与产物行各有一个「另存为」，弹出系统保存对话框。

- **改了计划里的口径，理由写在代码里**：原计划要 `fsWrite` + `artifactExport` 两条。只做一条 `fs/export`。`fsWrite` 会让 renderer 指定写盘目标，等于在「改动必留审阅记录、可回滚」的证据链上开一个后门；导出是单向的——源必须已在授权根内（复用 `fs/reveal` 的 `resolveRealOpenablePath`），目标由系统对话框返回，renderer 全程说不了目标路径。于是 `fs/export` 相较读盘**零新增权限**：一个本来就能打开的文件，被放到用户自己选的地方。
- **`sanitizeExportName` 是唯一能在 renderer 影响默认文件名的入口**，所以它只产出裸文件名：分隔符与保留字符折成 `-`，`.`/`..` 归空，长度截到 120。
- **保存到源文件本身**不当成错误：对话框已经让用户确认过覆盖，而 `copyFile` 会拒绝同源同目标，所以显式短路返回成功。
- **取消要安静**：用户按取消不是失败，不弹 toast；只有写入抛错才给错误提示。这层判断收在 `lib/export-file.ts`，两个调用点共用。
- **产物行的按钮是兄弟节点不是子节点**：文件行本身就是按钮，嵌套按钮会让两个控件都无法被正确标注；导出按钮放在 `<li>` 里的兄弟 `<span>`，hover / `focus-within` 才显形，长列表仍是一列文件名。
- 落点：`packages/shared/src/protocol.ts`、`types/filesystem.ts`、`electron/main/ipc/workspace-ipc.ts`、`src/lib/api.ts`、`src/lib/export-file.ts`（新）、`FilesTab.tsx`、`ArtifactsTab.tsx`、`styles/work-panel.css`、8 语言 `panel.files.{export,exported,exportError}`

### W-13 PDF 生成 ✅

`/pdf` 或命令面板「导出任务为 PDF」：当前会话 → PDF → 保存对话框，一步到位。

- **渲染在谁手里是分清的**：renderer 负责文档长什么样（Markdown 用与面板同一个 `marked` 解析器转 HTML），主进程负责窗口和文件。这样页面上没有任何脚本能自己够到网络或磁盘，也不必让主进程理解 Markdown。
- **窗口是消耗品**：`show: false` + `sandbox` + 无 node，`loadFile` 后 `printToPDF`，`finally` 里 `destroy()` 并删掉中间 HTML。中间文件用点号开头写在目标旁边，Chromium 只肯打印自己加载的文件，除此之外没有多余状态。
- **落在 scratch，让导出继续走 `fs/export`**：PDF 不是新的写盘通道，而是先落进文件面板本来就能读的 scratch 目录，再由 W-14 那条通道弹保存框。两条通道各自只做一件事。
- **正文按「文档」约束**：4 MiB 上限直接拒绝——超过这个量的页面是缺陷不是文档；工具行与系统提示被丢掉，PDF 里只留对话双方，因为这是给人读、给人转发的。
- **登记进命令注册表，顺带补上 spec**：`builtin.session.exportPdf` / `/pdf` 加进 `BUILTIN_COMMANDS`；`test/builtin-commands.test.mjs` 是集合守卫，所以双语 spec 的命令表与别名表同步加行——这个测试挡住的正是「悄悄多一个内置命令」。
- 落点：`protocol.ts`、`types/filesystem.ts`、`workspace-ipc.ts`、`src/lib/api.ts`、`src/lib/session-pdf.ts`（新）、`src/lib/export-session-pdf.ts`（新）、`src/lib/commands.ts`、`electron/main/builtin-commands.ts`、8 语言 `panel.files.{pdfUser,pdfAssistant,pdfEmpty,pdfFallbackTitle,pdfError}`、双语 `04-builtin-commands.md` 与 `01-ipc-protocol.md`

### W-16 变更追踪增强 ✅

审阅标签按文件分组，组头可回退整个文件；每行可跳回产生它的那条消息。

- **文件才是审阅单位**：一个文件被编辑五次是五个快照、一个文件。平铺列表把「这轮只动了一个文件」埋掉了。分组按路径、按路径排序（与文件树同序），组头给合计 +/- 与快照数。
- **回滚必须倒序**：快照是链式的，第 2 次编辑的还原基线建立在第 1 次之后的状态上。`rollbackTargets` 在分组时按消息顺序收集再 `.reverse()`，store 串行调用——顺序反了会把文件还原成中间态。
- **失败不静默**：`rollbackWorkspaceChanges` 返回 `{ rolledBack, failed }`；全成功提示「已回退该文件的全部改动」，有失败则「已回退 N 项，M 项未能回退」，行内状态保持可见。单条回滚入口原样保留。
- **定位复用转写自己的滚动权**：`locateTranscriptMessage` 只做 `[data-message-id]` 查询 + `scrollIntoView`，不新增「当前消息」状态；高亮用 `transcript-locate-target` 动画，并像搜索命中一样抬起 `content-visibility`，否则离屏行不会进入稳定布局。
- **卡片不重复渲染**：`ReviewChangeCard` 仍逐快照渲染，分组只负责外层；聊天流里的卡片不受影响（`onLocate` 只在审阅面板传）。

### W-17 运行日志面板 ✅

工作面板新增「日志」标签：把应用自己写下的 NDJSON 读回来，可切通道、按级别过滤、搜索、跟随尾部。

- **读文件，不新增推送通道**：日志本来就是落盘的 NDJSON（`<data_dir>/logs/<channel>/<category>.log`），缺的只是一个读回它的入口。`log/tail` 只读，渲染器拿到的结构和写盘那份同源，不维护第二套日志模型。
- **只读尾部窗口**：每个文件按 256 KiB 从末尾读，先丢掉窗口首行的残片（窗口几乎总是从行中间开始），再丢掉解析不了的行。这样被 kill 掉的写入进程留下的半行不会连带遮蔽它前面的整份日志——这正是「崩溃后第一件想做的事」。
- **轮转文件不混进来**：只认 `<category>.log`，`*.N.log` 是面板没索要的历史；真截断了由 `truncated` 说明，而不是拿一堆旧行冒充当前状态。
- **未知通道 / 级别报错而不是给空列表**：`sanitizeLogRequest` 对不在 `app|host|agent`、`debug|info|warn|error` 里的值抛 `INVALID_ARGUMENT`。空列表会被读成「没有日志」，这比报错更容易误导人。
- **过滤与计数留在渲染端**：`filterLogRecords` / `logLevelCounts` 是纯函数，输入、改级别、改搜索词都不走 IPC；主进程只负责「给我最新的 N 行」。级别过滤在主进程也做了一次（先过滤再截断），否则 `limit` 会把目标级别的行挤出去。
- **轮询 2s 而不是订阅**：host 通道的日志由另一个进程写文件，订阅最终还是要轮询一个文件，只会多一层机制。2 秒比人读得快。
- **截断必须可见**：窗口裁掉字节或匹配行数多于 `limit` 时面板明说「只显示最近 N 条」，避免「以为看到了全部」。
- 落点：`packages/shared/src/types/logs.ts`（新）、`packages/shared/src/protocol.ts`、`electron/main/log-tail.ts`（新）、`electron/main/ipc/log-ipc.ts`（新）、`electron/main/ipc/register.ts`、`src/lib/api.ts`、`src/lib/log-filter.ts`（新）、`components/workpanel/LogTab.tsx`（新）、`components/workpanel/WorkPanel.tsx`、`src/lib/work-panel-tabs.ts`、`styles/work-panel.css`、8 语言 `panel.tabs.log` 与 `panel.log.*`

### W-12 office 三件套 ✅

内置插件 `pi.office` 注册三个工具：`OfficeDoc` / `OfficeSheet` / `OfficeSlides`，一步生成 `.docx` / `.xlsx` / `.pptx` 落到工作区。

- **交付形态与方案原稿不同**：仓库里没有 `docx` / `exceljs` / `pptxgenjs`，也没有离线包，所以「依赖打进插件包」不成立。改为零依赖自拼 OOXML：`zip.js` 是 store-only ZIP（自带 CRC32、固定时间戳、可重现），`docx.js` / `xlsx.js` / `pptx.js` 各自输出最小但关系链完整的部件集（docx 7 件、xlsx 8 件、pptx 15 件）。收益是插件包只有几十 KB、没有供应链面；代价是只能覆盖「标题 + 段落」「表头 + 字符串单元格」「标题 + 要点」这类基础排版，复杂样式要另做。
- **产物落工作区而不是 `scratch/<sessionId>`**：产物标签的数据源是 `Write`/`Edit` 的 review 记录（`src/lib/task-artifacts.ts`），写到 scratch 用户既看不到也无从打开；写进工作区后文件面板与聊天里的路径链接都能直接接住。
- **新增宿主能力 `pi.fs.writeBase64`**：插件 fs 原本只有 `fs.writeText`，而 zip 容器一旦按 UTF-8 写就必然打不开。新 API 与 `fs.writeText` 共用同一套 `fs.write` 权限、manifest scope、拒绝名单、写入记录与审计（`api: "fs.writeBase64"`）；非法 base64 直接 `INVALID_ARGUMENT` 而不是解码成半个文件，单次上限 32 MiB。

### W-19 富格式预览 ✅

文件面板里点开 `.docx` / `.xlsx` / `.pptx` 直接看到内容，不再是「二进制无法预览」。方案原稿的路子是「转 HTML 交内嵌浏览器（mammoth / SheetJS）」，这里改成**主进程解析成结构化 JSON、渲染端用 React 画**。

- **为什么不转 HTML**：`mammoth` / SheetJS 都不在仓库里，也没有离线包；而且把文档转成 HTML 再塞进 `BrowserPreview`，等于把解析结果当不可信标记语言渲染，`<img onerror>` 一类注入要另做一层清洗。现在解析器只产出 `string[][]` 与纯文本块，渲染端是 `<table>` / `<p>` / `<li>`，**没有一处 `dangerouslySetInnerHTML`**。
- **零依赖自写 ZIP + XML**：容器支持 method 0（store）与 method 8（deflate，`zlib.inflateRawSync`），从 EOCD 反向找中央目录、逐条校验大小与中央目录一致；XML 用局部名匹配（`w:p` → `p`），容忍命名空间前缀变化。**必须支持 `xl/sharedStrings.xml`**——真实 Excel 存的都是共享字符串表，只有我们自己 `pi.office` 的产物是 `inlineStr`，两条路径都有测试（这正是「生成器能打开、真实文件打不开」的典型坑）。
- **上限与截断明说**：文件 16 MiB、块 2000、表行 200、sheet 20、sheet 行 500、列 64、页 200、单块 5000 字符。任一超限置 `truncated: true` 由界面提示，**不抛错**；zip 损坏、缺 `word/document.xml` → `unsupported/corrupt`，渲染端回落到「用系统默认程序打开」，不给用户看白屏或半张表。
- **不把绝对路径写进错误**：路径仍走 `resolveOpenablePath` 收口，越界给 `PATH_OUTSIDE_WORKSPACE`、不存在给 `NOT_FOUND`，两者都不回显原路径（一份 docx 的路径可能带客户名）。

## 6. 已知债务与口径偏差

1. **W-08 的看门狗在 renderer 内**，没有 `electron/main/runtime/watchdog.ts`。三档语义等价（单调升档 → 每档只播一次），但「应用在后台时是否也计时」取决于窗口是否被节流，未做专门验证。
2. **W-05 不落库**（有意为之）：方案原写改 Rust plans 表，实际用「快照 + 工具行重放」。收益是不加迁移、重启天然一致；代价是步骤只在**批准过的计划**里存在，普通 agent 会话没有步骤条（这符合预期）。
3. **W-10 后台会话进度可能滞后**：会话切走后 pane 保留的是最后画面，侧栏显示会停住，切回即校正。要彻底实时，需要把 `UpdateStep` 事件按 sessionId 投影进 store，属于新增第二份状态，暂不做。
4. **W-03 落点在顶栏**而非 `transcript/`，§11 已注明。
5. **W-34 未按方案重做**：既有 MCP 市场已覆盖大部分需求，建议先做一次体验走查再决定是否补工。
6. **W-04 复用 asktool 通道**，没有新增「待确认事件」，确认条也不在 `ToolRow` 而在 `AskToolCard`。副作用是这条提问会出现在 asktool 的队列里（`queued` 计数会 +1）；语义上它确实是一次「需要人回答的往返」，但若后续要让两者在 UI 上彻底分开，需要给 `asktool_request` 加一个 `kind` 字段。
6b. **W-12 的产物不进「产物」标签**：产物标签读的是 `Write`/`Edit` 的 review 记录，插件用 `fs.writeBase64` 写的 docx/xlsx/pptx 不产生 review 记录。当前靠工具返回值里的路径让聊天渲染文件链接；要让它们出现在产物标签里，得给 review 记录补一条「插件写入」来源，属于 W-19 之后的口径问题。
6c. **W-19 的观感未经真实窗口验证**：预览的断言全部落在「解析结果 + 渲染契约」上（结构化 JSON 正确、表格语义、截断标志、8 语言键），没有在跑起来的 Electron 里看过长表横滚、16:9 卡片在窄面板下的比例、深色主题下纸张视图的对比度。这类问题只能在真实窗口里发现，属下一轮手测项。
6d. **`@pi-desktop/shared` 的 `dist` 不提交**：新增 `preview.ts` 后必须先 `pnpm -C packages/shared build`，否则桌面端 `typecheck` 会报「`@pi-desktop/shared` has no exported member `DocumentPreviewResult`」，运行时 `IPC.invoke.documentPreview` 也会是 `undefined`。这不是缺陷，是「包产物不入库」的固有代价，但第一次踩到时会像类型写错。
